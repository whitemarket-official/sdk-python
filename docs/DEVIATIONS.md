# Deviations from SDK_SPEC (Python)

Every place where this SDK deviates from [`SDK_SPEC.md`](SDK_SPEC.md), with the reason (CLAUDE.md rule 17).

| Spec section | What the spec requires | Why it does not fit Python (fact) | What this SDK does |
|---|---|---|---|
| 1.5 "Errors" | `NotFoundError` when "category ends with `.not_found`" | The spec does not say which error of a multi-error response decides | `NotFoundError` only when EVERY error's category ends with `.not_found`; a mix (or an answer with no errors) gives a plain `GraphQLError` (`GraphQLError.has_category()` finds a category in any error). Same as PHP; proposed for SDK_SPEC clarification |
| 1.5 "HttpError body excerpt" | A JSON body is "re-encoded compactly"; integers beyond 64 bits stay exact | PHP re-encodes a JSON float through `serialize_precision=-1` (`1e2` -> `100.0`, `1.50` -> `1.5`, `1e400` fails and the body falls back to text); Python's `json` has no such canonical float form, and a re-encoding that changed numbers would be worse than none | Floats keep their original JSON text (`1e2` stays `1e2`). Only floats differ from the PHP SDK; found by a differential run of 20k generated bodies against `BodyRedactor` (zero other differences). Strings, keys, 64-bit ints, depth, size and escapes match |
| 1.3 "Timeouts": request 30 s | One bound on the whole request | httpx timeouts are per phase (connect, read, write, pool) and there is no total timeout [docs https://www.python-httpx.org/advanced/timeouts/]. The async client can wrap the request in `asyncio.timeout`; a blocking sync read cannot be interrupted | Async: a hard limit on the whole attempt, body included (`AsyncDeadline`). Sync: the deadline is checked between body reads and every phase is bounded by `request`, so one attempt ends within `request` plus one read timeout (about 2 x 30 s worst case on the default settings). Not applied to an injected `http_client`. ADR 0002 |
| 2 "TokenStore" / "TokenProvider" | One protocol each | The same protocol cannot serve both clients: a store or provider used by the async client must be awaited | Twins by the unasync rule: `TokenProvider` / `TokenStore` / `InMemoryTokenStore` (sync) and `AsyncTokenProvider` / `AsyncTokenStore` / `AsyncInMemoryTokenStore`; same method names (`access_token`, `refresh`; `get`, `set`, `clear`). `get()` returns `StoredToken` (a `NamedTuple`, `(token, expires_at)`). Public API shape: owner to confirm |
| 8 "Secrets in traces" | Credentials excluded from stack traces where the runtime records call arguments | Python has no `#[SensitiveParameter]`; a traceback does not print arguments, but a debugger or a `traceback` with locals would show frame variables | Credentials are `Secret` everywhere they are stored or passed (header dicts hold `Secret`); the plain text exists only in the httpx request built for one attempt. httpx errors (which hold the request) are never chained: `TransportError` is raised after the `except` block, `__context__` and `__cause__` are `None` (tested) |
| 1.1 "Generated layer": `execute(...)` | `execute(document, variables)` | Python generated methods need to pass the type | Extra keyword-only `operation_type=None` on `execute`; `None` infers it as PHP does (only a clear query is a query). A declared `"query"` can only downgrade to a mutation: the executor re-infers the type from the document, so no caller can make a mutation document retryable (rule 2; stricter than PHP, whose executor trusts the declared type) |

## Accepted limitations

Behaviour that matches the PHP SDK and is kept on purpose; each row names the owner decision or the reason.

| Where | Limitation | Why it is accepted |
|---|---|---|
| `schema/partner.graphql`, `schema/partner.introspection.json`, generated docstrings (`src/whitemarket/_generated/**`) | Server `@example` texts contain Steam trade URLs with `partner` and `token` values and Steam-ID-shaped numbers | Owner decision 2026-11-14: public partner-doc examples; the owner checked that the example trade URLs are no longer valid (Steam: "no longer valid for sending a trade offer"). They are not scrubbed (the schema is a byte-identical server snapshot shared by all SDKs). Reviewers and security reviews must not flag them again |
| `errors.GraphQLError` | The exception text is the server's `errors[0].message` verbatim, and `errors[*].message`, `extensions` and `partial_data` are raw server data, not redacted. Only the root fields that carry a credential (`auth_token`, `auth_steam_jwt`, `profile_steam_proxy_get`) are removed from `partial_data` | Callers act on the message and the category; the server is not expected to echo credentials in GraphQL errors (PHP DEVIATIONS `Errors\GraphQLException`) |
| `_async/graphql.py` (401 replay) | The replay after a 401 is a second `transport.post` with its own attempt budget: a query can send up to 2 x `max_attempts` requests (503, 503, 401, 503, 503, 503 is 6 sends with `max_attempts=3`) | Same as PHP `GraphQLExecutor::postWithOneReplay`; the total stays bounded. Whether the budget should be shared across the replay is proposed for SDK_SPEC 1.4 |
| `parse_retry_after` (`_runtime/retry_after.py`) | An unparsable `Retry-After` on a 429 or 503 counts as no header: the query is retried with the SDK's own backoff | Same as PHP `RetryAfter`; bounded by `max_attempts` |
| `_runtime/jwt.py` | A token whose `exp` is already past (or an `iat`-based lifetime longer than the real one) is kept for the lifetime rule of ADR 0003 (24 h at most, never below 10 minutes); the server's 401 then triggers the one refresh and replay | Same rule as PHP `JwtExpiry` and ADR 0003: counting from the local clock keeps a skewed host clock from re-exchanging on every call. Owner to confirm (see the report of the 2026-11-14 fix round) |

## Exports (pure half: rows, decoders, meta, links)

| Spec section | What the spec requires | Why it does not fit Python (fact) | What this SDK does |
|---|---|---|---|
| 3.10 rule 10, 12 (JSON row cap) | A row over 128 KiB of text is refused "with every parser"; a parser that cannot see row boundaries may read a small fixed read-ahead past the limit | `ijson` reports no offsets, so row boundaries are not visible | The input is handed to the parser in steps of 4096 bytes and counted since the last finished row: a row up to 128 KiB is never refused, one over 128 KiB + 3 steps (12 KiB) always is, in between either may happen |
| 3.10 rule 12 (integer range) | An id is never rounded; a parser that cannot keep an integer beyond 64 bits fails the row | `ijson` 3.6.0 with the C backend (`yajl2_c`) crashes the interpreter (segmentation fault) on an integer token longer than `sys.get_int_max_str_digits()` digits (4300 by default), observed on CPython 3.13 with 4301 nines; the pure Python backend raises instead | Any run of more digits than that limit in a JSON row (a number, or a digit string) is a `DecodeError` at the row, for every backend, checked before the bytes reach the parser. Integers up to 4300 digits are kept exact (no 64-bit limit). Not applied when the interpreter has no limit (`0`) |
| 3.10 rule 12 (nesting) | A row nested deeper than 511 levels is refused | The check runs on the finished row (iteratively), not while parsing | Same result; memory is bounded by the row cap, not by the depth |
| 3.10 rule 8 (`deliveryPromise`) | `10min`, `1hour`, `12hours`, `24hours` map to the enum; any other value is the unknown variant | `DeliveryPromise("HOUR1")` is the declared member, an enum name sent as a wire value gives the member, not the unknown variant | Only observable through `is_unknown` on a server value that equals an enum name (`HOUR1`); the value compares equal either way |
| 3.10 rule 11 (CSV record cap) | A record over 128 KiB is refused | The decoder cuts records from decoded text | The cap counts the UTF-8 bytes of the record (exact for multi-byte text), line end excluded |
| 3.10 rule 5, 8 (ids) | Ids are digit strings; a float token is a `DecodeError` | `bool` is an `int` in Python, `-0` is an integer token | A JSON `true` is not an id; `-0` is the integer 0 and becomes `"0"` |
| 3.10 `streamPrices` | Iterator over price rows | The async client cannot yield from a coroutine that already holds the whole body | `stream_prices` is a coroutine in the async flavor (requests sent at the call, like PHP): the bounded body is read and parsed, then the rows are replayed. `stream_products` likewise returns a closable stream object (`aclose()`/`close()`, context manager) instead of a bare generator, so the connection can be closed even if never iterated |
| 3.10 rule 2 (redirects) tests | Redirect rules over https | The SDK has no switch for plain http; loopback servers have no TLS certificate | Tests widen `_runtime.endpoints._ORIGIN_SCHEMES` to cover redirects over real sockets (cross-port refused, same-origin followed); the same-host https redirect is tested with a mock transport and the pure `redirect_target` unit tests |

## Live (SSE and WebSocket)

| Spec section | What the spec requires | Why it does not fit Python (fact) | What this SDK does |
|---|---|---|---|
| 3.11 / 8 logging (SSE) | Tokens never logged | `httpx` logs the SSE request URL, which holds `cf_connect` (the connect command with the token), at INFO | A `logging.Filter` on the `httpx` logger redacts the query of that record while an SSE connection exists. The WebSocket side needs no filter: `websockets` gets the SDK's own logger pinned to INFO, so frames (token, Steam ids) are never logged (ADR 0005) |
| 3.11 SSE reader | `aiter_lines` (project plan) | `httpx` `aiter_lines` splits like `str.splitlines` (U+2028, U+0085 end a line, which SSE does not allow) and has no size cap | `aiter_bytes()` with `SseParser` (CR, LF, CRLF; per-line and per-event cap) |
| Brief / plan: "connection code in `_async`, sync generated by unasync" | The sync client gets live from the generated twin | The connection code uses the asyncio API of `websockets` and `httpx`, and the pull engine needs reader tasks for both transports | Engine and connections live in `whitemarket/live/` (async only). `LiveSession` (sync) runs the engine on a private event loop thread; handlers run on the caller's thread. `client.live()` is generated by unasync from `_async/client.py` and returns `LiveSession` there. ADR 0005 |
| 3.11 slow consumer | Not stated; PHP is single-threaded and never buffers (a message is read when `poll()` asks) | The WebSocket reader task must keep reading to answer the server ping (a missing pong closes the connection) while the consumer may be slow | The reader task puts decoded messages into a bounded queue (`min(4096, 64 MiB / max_message_bytes)`, at least 2; SSE: the same size, and the reader stops reading, TCP backpressure). On WebSocket overflow the connection is closed (1008) and reported as a slow consumer: `on_error` gets a `LiveConnectionError` (no code), the session reconnects with backoff and `on_connected(reconnected=True)` tells the user to resync. Messages already buffered are dropped with the connection |

## Buying and deals

Rows marked **owner approval** touch money, retry or idempotency: they follow the PHP reference's outcome and are listed here for the owner to confirm.

| Spec section | What the spec requires | Why it does not fit Python (fact) | What this SDK does |
|---|---|---|---|
| 3.3 rule 6 (malformed error entries) **owner approval** | A 200 with errors on a nested path means the purchase ran: reconcile. PHP turns a malformed `errors[].path` (a null, float, bool or object segment, a dotted string), an entry that is not an object and a missing or non-string `message` into a `DecodeException`, which reconciles | `GraphQLError.from_payload` is tolerant by design (`tests/unit/errors/test_errors.py`): a malformed `path` reads as "no path", which is the signature of a root rejection, so a nested error could look like "the deal was not created" and a purchase would not be reconciled | `GraphQLErrorEntry.malformed` is true for such an entry; `_runtime/rejection.is_mutation_rejection` never counts an error list with a malformed entry as a rejection, so the purchase is reconciled, as in PHP. The parse and the exception class stay as they were |
| 3.3 rule 6 (`data: {}`) **owner approval** | `data` that is an empty object with a root-path error is ambiguous: reconcile | The executor stripped credential fields from `partial_data` with `kept or None`, so an empty `data` object arrived as `None` ("no data"), i.e. a clean rejection | `partial_data` stays `{}` for an empty `data` object, and a `data` that held nothing but credential fields becomes `{}` too (round 4: it used to become `None`, which read as "no data" and turned `{auth_token: ...}` plus a root-path error into a clean rejection); only an absent or null `data` is `None` |
| 3.3 (what is reconciled) **owner approval** | Every failure of `market_buy` except the rejections is reconciled (PHP catches any `Throwable`) | A Python task cancellation (`asyncio.CancelledError`), `KeyboardInterrupt` and `SystemExit` derive from `BaseException`; sleeping 10 to 20 s and polling while the caller is being cancelled would hold up the cancellation | `Exception` is reconciled (unexpected exceptions included); a `BaseException` that is not an `Exception` propagates at once and the caller can not tell whether the purchase happened. Pass and persist your own `custom_id` before calling when that matters, and look the deal up by it afterwards |
| 3.3 `custom_id` | 1..100 characters of valid UTF-8 | A Python `str` can hold a lone surrogate that has no UTF-8 form | Length counts code points; a lone surrogate is a `ValueError` |
| 3.3 `tradeUrl` | `link` option of a purchase | A Python caller may keep the URL in a `Secret` | `trade_url` is a `str` or a `Secret`; either way it appears in no error, repr or log. A failed buy's traceback frames hold the caller's argument, as in any language |
| 3.4 rule 4 and `opts.live` (matching) | `waitFor` wakes on a deal event of the waited deal, ids compared without regard to case (PHP `strcasecmp`) | `AsyncLiveSession.wait_for_deal_event(deal_id, timeout)` (SDK_SPEC 3.11, owned by the live module) compares the id exactly | The wait passes the id spelling the statuses or `get()` reported (the server's own); before any state is known it passes the lower-cased UUID reference. An event that differs only in case from that spelling would not wake the wait early; the next scheduled poll still happens |
| 3.4 rule 4 (closed live session) | A closed session returns at once and the wait sleeps the rest of the interval | `wait_for_deal_event` returns `None` both after the full wait and when the session is closed | The wait compares the clock before and after: time left on the interval is slept, so a closed session never makes the loop spin |
| 3.4 `statuses` | Result is a map keyed by the requested string | PHP turns decimal-integer keys into ints | A Python `dict[str, DealState]` keeps every key a `str` |
| 3.4 `waitFor` clock | Elapsed time is wall-clock | A wall clock (`time.time`) steps with NTP or a manual change: a step back extends the wait (observed: 723 sleeps for a 12 s timeout) | `time.monotonic` is the default clock: still elapsed real time, not moved by a system clock change. The clock and the sleeper are injectable (`AsyncDealsApi(clock=, sleeper=)`) |
| 3.3 rules 1-2 (reconciliation lookup) | The deal found by `custom_id` is the purchase | A lookup that answers another deal (a server or proxy fault) would come back as `reconciled=True` for a deal the caller never bought; PHP has no such check | **Stricter than PHP:** a deal whose `custom_id` differs from the one looked up (or has none) is a failed lookup (`DecodeError` kept as `last_lookup_error`) and the attempts go on. PHP parity change proposed |
| 3.4 `opts.live` (burst of events) | `waitFor` re-checks the state when a deal event of the waited deal arrives | Taken literally (PHP does) a burst of events is a burst of back-to-back `deal_buyer_statuses` requests | **Differs from PHP:** two polls begin at least 1 s apart (`MIN_EVENT_POLL_GAP`); an early wake is held until then, never past the poll interval or the deadline |
| 2 `BuyReconciliation` (types) | `attempts` is an int, `interval` finite and not negative | Python does not enforce annotations: `attempts=2.5`, `True`, an infinite or NaN `interval` were accepted | `attempts` must be a whole `int` (not a `bool`, `TypeError`), `interval` finite and >= 0 (`ValueError`), as PHP's typed signature and `is_finite` checks |
| 3.3 (inputs before the send) | A bad argument raises before anything is sent | A text the JSON encoder refuses (a lone surrogate in a product id, name hash, asset id or trade URL) failed inside the `try` of `market_buy` and cost a full reconciliation | Every string argument is checked (`TypeError` for a non-`str`, `ValueError` for invalid Unicode, without the text) before the request is built |
| 1.1 / 3.10 injected `http_client` | An injected client is used as is | A client built with `follow_redirects=True` follows a redirect (with a custom credential header) before the SDK can refuse it; default headers, cookies and `auth` of the client travel to the export host. httpx applies them in `build_request` / `send` [code httpx 0.28 `_client.py`] | Every SDK request is sent with `follow_redirects=False` and `auth=None`; export requests are built without the client's default headers and cookies. The client's timeouts, transport, proxies and event hooks still apply (ADR 0002) |
| 3.10 rule 9 "stopping closes the connection" | Leaving a row iteration early closes the connection | Python runs no code when a `for` / `async for` loop is left with `break`, and an async generator cannot be closed synchronously [docs https://docs.python.org/3/reference/expressions.html#asynchronous-generator-functions]. The sync stream can close at once from `__del__`; the async one can only schedule the close | `with` / `async with` / `close()` / `aclose()` close it at once (documented as the way to stop). A stream dropped open is closed when it is garbage collected: at once (sync) or as a task on the running event loop (async; without a running loop nothing can close it) |

## Selling (SDK_SPEC 3.5)

| Spec section | What the spec requires | Why it does not fit Python (fact) | What this SDK does |
|---|---|---|---|
| 3.5 `selling.list(item, price, opts{...})` **owner approval** | The delivery type, promise and lifetime travel in one `opts` object (PHP: `?ListingOptions`) | The task brief for this SDK asks for keyword-only arguments, the Python idiom for optional values; the validation is the same | `list(item, price, *, delivery_type=SEMI, delivery_promise=None, lifetime=None)` builds a `ListingOptions` internally (so the rules are written once); `list_many(items, options)` takes the object. Public API shape: sister SDKs keep one options object |
| 3.5 rule 3 "A request (chunk) that fails ... `NotSent`" (401) **owner approval** | The classification of 3.3 rule 6: HTTP 400, 401, 429 reject | PHP's selling tests treat an `AuthenticationException` thrown by the HTTP client as ambiguous, because the PHP transport refreshes outside the client; the Python executor refreshes and replays once and raises `AuthenticationError` only after the second 401, which proves nothing ran | `AuthenticationError` is a rejection (`NOT_SENT`), as in `is_mutation_rejection` |
| 3.5 rule 4 (unusable `index`) | An `index` outside the chunk or repeated makes "the chunk `Unknown`" | Rule 3 says a failing chunk stops the batch, rule 4 does not say whether this counts as one; PHP stops | The chunk is `UNKNOWN`, later chunks stay `NOT_SENT` and are never sent, earlier chunks keep their results, and `BatchIncompleteError.__cause__` is a `DecodeError` naming `<field>[i].index`. The same for a cross-check mismatch (rule 7), path `<field>[i].product.id` |
| 3.5 rule 8 (malformed error entry) | A batch GraphQL error is a rejection only when there is no `data` key and every error has no path | A malformed `errors[].path` parses as "no path" | Such an entry is never a rejection (the chunk is `UNKNOWN`), as in `is_mutation_rejection` |
| 3.5 rule 3 (cancellation) | (silent) | `asyncio.CancelledError` is not an `Exception` | A cancelled `*_many` call propagates the cancellation and returns no results; the request in flight may have run, check `my_products()` |
| 3.5 rule 7 (cross-check) **proposed SDK_SPEC change** | A row's product is compared with the item requested at its position | The check ran on the decoded product; a product whose price or wear did not decode (`DecodeError`) became "no product", so the check was skipped and a row for another item read as `SUCCEEDED` (found by the round-5 verifier) | The identity (listing id, item id, asset id) is read from the raw row before any money or wear is decoded; a mismatch makes the chunk `UNKNOWN` even when the rest of the row cannot be decoded. To add to SDK_SPEC 3.5: "identity is checked before money and wear decode" (sister SDKs to confirm) |
| 3.5 rule 3 (a chunk that cannot be encoded) | (silent) | An unencodable value (a float or non-finite `Decimal`, text with a lone surrogate) fails before any byte is sent, yet the chunk was reported `UNKNOWN` like an ambiguous failure | `RequestNotSentError` (a `ValueError` and a `TypeError`, private to `_runtime.json_codec`) is raised by the request encoder; it counts as a rejection for single mutations and batches: the chunk is `NOT_SENT`, a purchase is not reconciled. `ListingOptions.lifetime` and `set_lifetime_for_all` also refuse a non-`int` (a `float`, `Decimal`, `bool`) with `TypeError` at the call (SDK_SPEC 3.5 rule 6) |
| 1.5 `GraphQLError` | (silent) | Rule 8 needs "no `data` key" apart from `data: null`, which `partial_data` cannot tell | New attribute `data_present`, set by the executor from the response; default: `partial_data is not None` for an error built by hand |
