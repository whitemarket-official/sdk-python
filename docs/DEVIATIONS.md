# Deviations from SDK_SPEC (Python)

Every place where this SDK deviates from [`SDK_SPEC.md`](SDK_SPEC.md), with the reason (CLAUDE.md rule 17).

| Spec section | What the spec requires | Why it does not fit Python (fact) | What this SDK does |
|---|---|---|---|
| 1.5 "Errors" | `NotFoundError` when "category ends with `.not_found`" | The spec does not say which error of a multi-error response decides | `NotFoundError` only when EVERY error's category ends with `.not_found`; a mix (or an answer with no errors) gives a plain `GraphQLError` (`GraphQLError.has_category()` finds a category in any error). Same as PHP; proposed for SDK_SPEC clarification |
| 1.5 "HttpError body excerpt" | A JSON body is "re-encoded compactly"; integers beyond 64 bits stay exact | PHP re-encodes a JSON float through `serialize_precision=-1` (`1e2` -> `100.0`, `1.50` -> `1.5`, `1e400` fails and the body falls back to text); Python's `json` has no such canonical float form, and a re-encoding that changed numbers would be worse than none | Floats keep their original JSON text (`1e2` stays `1e2`). Only floats differ from the PHP SDK; found by a differential run of 20k generated bodies against `BodyRedactor` (zero other differences). Strings, keys, 64-bit ints, depth, size and escapes match |
| 1.3 "Timeouts": request 30 s | One bound on the whole request | httpx timeouts are per phase (connect, read, write, pool) and there is no total timeout [docs https://www.python-httpx.org/advanced/timeouts/]. The async client can wrap the request in `asyncio.timeout`; a blocking sync read cannot be interrupted | Async: a hard limit on the whole attempt, body included (`AsyncDeadline`). Sync: the deadline is checked between body reads and every phase is bounded by `request`, so one attempt ends within `request` plus one read timeout (about 2 x 30 s worst case on the default settings). Not applied to an injected `http_client`. ADR 0002 |
| 2 "TokenStore" / "TokenProvider" | One protocol each | The same protocol cannot serve both clients: a store or provider used by the async client must be awaited | Twins by the unasync rule: `TokenProvider` / `TokenStore` / `InMemoryTokenStore` (sync) and `AsyncTokenProvider` / `AsyncTokenStore` / `AsyncInMemoryTokenStore`; same method names (`access_token`, `refresh`; `get`, `set`, `clear`). `get()` returns `StoredToken` (a `NamedTuple`, `(token, expires_at)`). Public API shape: owner to confirm |
| 8 "Secrets in traces" | Credentials excluded from stack traces where the runtime records call arguments | Python has no `#[SensitiveParameter]`; a traceback does not print arguments, but a debugger or a `traceback` with locals would show frame variables | Credentials are `Secret` everywhere they are stored or passed (header dicts hold `Secret`); the plain text exists only in the httpx request built for one attempt. httpx errors (which hold the request) are never chained: `TransportError` is raised after the `except` block, `__context__` and `__cause__` are `None` (tested) |
| 1.1 "Generated layer": `execute(...)` | `execute(document, variables)` | Python generated methods need to pass the type | Extra keyword-only `operation_type=None` on `execute`; `None` infers it as PHP does (only a clear query is a query). A declared `"query"` can only downgrade to a mutation: the executor re-infers the type from the document, so no caller can make a mutation document retryable (rule 2; stricter than PHP, whose executor trusts the declared type) |

## Accepted limitations

Behaviour that matches the PHP SDK and is kept on purpose; each row names the owner decision or the reason.

| Where | Limitation | Why it is accepted |
|---|---|---|
| `errors.GraphQLError` | The exception text is the server's `errors[0].message` verbatim, and `errors[*].message`, `extensions` and `partial_data` are raw server data, not redacted. Only the root fields that carry a credential (`auth_token`, `auth_steam_jwt`, `profile_steam_proxy_get`) are removed from `partial_data` | Callers act on the message and the category; the server is not expected to echo credentials in GraphQL errors (PHP DEVIATIONS `Errors\GraphQLException`) |
| `_async/graphql.py` (401 replay) | The replay after a 401 is a second `transport.post` with its own attempt budget: a query can send up to 2 x `max_attempts` requests (503, 503, 401, 503, 503, 503 is 6 sends with `max_attempts=3`) | Same as PHP `GraphQLExecutor::postWithOneReplay`; the total stays bounded. Whether the budget should be shared across the replay is proposed for SDK_SPEC 1.4 |
| `retry.parse_retry_after` | An unparsable `Retry-After` on a 429 or 503 counts as no header: the query is retried with the SDK's own backoff | Same as PHP `RetryAfter`; bounded by `max_attempts` |
| `_runtime/jwt.py` | A token whose `exp` is already past (or an `iat`-based lifetime longer than the real one) is kept for the lifetime rule of ADR 0003 (24 h at most, never below 10 minutes); the server's 401 then triggers the one refresh and replay | Same rule as PHP `JwtExpiry` and ADR 0003: counting from the local clock keeps a skewed host clock from re-exchanging on every call. Owner to confirm (see the report of the 2026-11-14 fix round) |

## Exports (pure half: rows, decoders, meta, links)

| Spec section | What the spec requires | Why it does not fit Python (fact) | What this SDK does |
|---|---|---|---|
| 3.10 rule 10, 12 (JSON row cap) | A row over 128 KiB of text is refused "with every parser"; a parser that cannot see row boundaries may read a small fixed read-ahead past the limit | `ijson` reports no offsets, so row boundaries are not visible | The input is handed to the parser in steps of 4096 bytes and counted since the last finished row: a row up to 128 KiB is never refused, one over 128 KiB + 3 steps (12 KiB) always is, in between either may happen |
| 3.10 rule 12 (integer range) | An id is never rounded; a parser that cannot keep an integer beyond 64 bits fails the row | `ijson` 3.6.0 with the C backend (`yajl2_c`) crashes the interpreter (segmentation fault) on an integer token longer than `sys.get_int_max_str_digits()` digits (4300 by default), observed on CPython 3.13 with 4301 nines; the pure Python backend raises instead | Any run of more digits than that limit in a JSON row (a number, or a digit string) is a `DecodeError` at the row, for every backend, checked before the bytes reach the parser. Integers up to 4300 digits are kept exact (no 64-bit limit). Not applied when the interpreter has no limit (`0`) |
| 3.10 rule 12 (nesting) | A row nested deeper than 511 levels is refused | The check runs on the finished row (iteratively), not while parsing | Same result; memory is bounded by the row cap, not by the depth |
| 1.5 / 3.10 rule 4 (error path) | `DecodeError` path like `prices[3].price` | `DecodeError.path` is a tuple and its text joins the parts with `.` | `path == ("prices", 3, "price")`, text `prices.3.price`; no bracket form. Proposed: render integer parts as `[3]` in `DecodeError.__str__` (changes the shared error class, not done here) |
| 3.10 rule 8 (`deliveryPromise`) | `10min`, `1hour`, `12hours`, `24hours` map to the enum; any other value is the unknown variant | `DeliveryPromise("HOUR1")` is the declared member, an enum name sent as a wire value gives the member, not the unknown variant | Only observable through `is_unknown` on a server value that equals an enum name (`HOUR1`); the value compares equal either way |
| 3.10 rule 11 (CSV record cap) | A record over 128 KiB is refused | The decoder cuts records from decoded text | The cap counts the UTF-8 bytes of the record (exact for multi-byte text), line end excluded |
| 3.10 rule 5, 8 (ids) | Ids are digit strings; a float token is a `DecodeError` | `bool` is an `int` in Python, `-0` is an integer token | A JSON `true` is not an id; `-0` is the integer 0 and becomes `"0"` |
